# 技术选型调研：微信消息 → LLM 回复的外挂侧边栏

> 背景：有 Python 基础，**不会前端、不会后端**；目标 MVP（非生产级）。
> 数据时间：2026-10-20（GitHub API 实时）

---

## 一、需求对齐与硬约束

**一句话需求**：Windows 本机运行，接收微信消息 → 交给大模型生成回复 → 在贴在微信右侧的侧边栏展示 → 一键填入微信输入框 / 直接发送。

### 三条硬约束（它们直接决定选型边界，比"喜不喜欢"重要）

| # | 约束 | 来源 | 对选型的强制影响 |
|---|---|---|---|
| 1 | **采集层只能是 Python** | wxauto 只有 Python 版；Windows UIA/剪贴板/窗口句柄操作在 Python 侧最成熟（`pywin32`/`comtypes`） | 无论前端用什么，"后端"必须在 Python 生态里选（FastAPI/Flask/无框架），或至少保留一个 Python 常驻进程 |
| 2 | **必须能拿到窗口句柄做 win32 控制** | 侧边栏要"无边框 + 置顶 + **点击不抢焦点** + 跟随微信位置" | UI 层必须能设置 `WS_EX_NOACTIVATE`、`HWND_TOPMOST`、`SetWindowPos` —— **纯浏览器里跑的 UI 直接出局** |
| 3 | **本机桌面 GUI，需要真实前台窗口** | wxauto 依赖微信窗口真实可见、可交互 | 排除云部署、Docker、纯 Web 服务 |

> 约束 2 是本项目最容易被忽略、也最容易导致返工的一条。很多人先选了最"简单"的 UI 框架，做到一半才发现窗口不能贴边/会抢焦点，全部推翻重来。

### 假设（如不成立请指出，结论会变）

1. 目标环境：Windows 10/11 + **个人微信 3.9.11.17**（wxauto 强绑定），单机自用
2. 无多用户、无并发、无权限体系；数据量小（消息 < 10 万条）
3. LLM 走云端 API（DeepSeek/OpenAI 兼容），不做本地推理
4. MVP 只需 Windows，不考虑 macOS/Linux

### In / Out（MVP）

**In**：接收当前会话消息、LLM 生成建议、手动改后发送、贴边跟随、不抢焦点、配置持久化
**Out**：多账号、自动全托管回复（风险高）、插件市场、云端同步、团队共用

## 二、候选方案

### 方案 A：Tauri 2 + React/TS + FastAPI + SQLite

| 层 | 选型 | 说明 |
|---|---|---|
| 前端 | React 18 + TypeScript + Vite，跑在 Tauri 的 WebView2 里 | 界面最精致；生态最大 |
| 后端 | FastAPI（uvicorn），REST + WebSocket | 与采集层同语言，AI 生成质量最高 |
| 数据库 | SQLite（`sqlite3` / SQLModel） | 零运维，单文件 |
| 部署 | `tauri build`（产出 msi/nsis）+ Python 后端单独 PyInstaller | **两个产物**，需 Rust 工具链 |

- 硬约束满足方式：窗口无焦点/贴边靠 **Python 侧 `services/docker.py` 按窗口标题找句柄**补上（Rust 壳本身不管这些）
- 现状：**这套已落地并跑通**（`wechat-sidebar/` 原型，vite build 通过、8 个接口全通、窗口已弹出）

### 方案 B：PySide6 + FastAPI + SQLite

| 层 | 选型 | 说明 |
|---|---|---|
| 前端 | **PySide6（Qt 官方 Python 绑定，LGPL）** —— 一个 Python 文件就是界面 | 不写 HTML/CSS/TS，不需要 Node 和 Rust |
| 后端 | FastAPI（保留）或纯函数调用 | 保留 FastAPI = 保留进程隔离（wxauto 阻塞时不卡 UI） |
| 数据库 | SQLite（`sqlite3` / SQLModel） | 同上 |
| 部署 | PyInstaller 打两个 exe（后端 + UI），或 `--onefile` 合一个 | 一条命令，无 Rust、无 Node |

- 硬约束满足方式：Qt 原生就支持 `Qt.Tool | Qt.FramelessWindowHint | Qt.WindowStaysOnTopHint | Qt.WindowDoesNotAcceptFocus`；**且现有 `docker.py`（win32 贴边/无焦点/Z 序补偿）一行不改直接复用**（它按窗口标题找句柄，与 UI 技术无关）

### 方案 C：NiceGUI / Streamlit / Gradio（纯 Python Web UI）

| 层 | 选型 |
|---|---|
| 前端 | NiceGUI（Python 写 UI，底层 Vue+Quasar）；或 Streamlit/Gradio |
| 后端 | 同上，或干脆合并成一个 Python 进程 |
| 数据库 | SQLite / JSON 文件 |
| 部署 | 浏览器打开 `localhost`；NiceGUI 有 `native` 模式（pywebview） |

- 硬约束满足方式：**基本无法满足**。浏览器标签页/窗口拿不到可控的 HWND，设不了 `WS_EX_NOACTIVATE`，做不了"点击不抢焦点"和"跟随微信右侧"。NiceGUI 的 native 模式底层是 pywebview，理论上能摸到窗口，但**官方没暴露置顶/无焦点/位置跟随的稳定 API**，属于冷门路径，AI 也容易给出错误答案 → 高概率返工。

### 方案 D（不推荐但很多人用）：Electron + Python sidecar

| 层 | 选型 |
|---|---|
| 前端 | Electron + React |
| 后端 | Python 脚本作为 sidecar 子进程，靠 stdout/HTTP 通信 |
| 数据库 | SQLite |
| 部署 | electron-builder 打包（约 150MB+） |

## 三、对比矩阵

评分 1–5，5 分最优。**"AI 支持度"拆成两个子维度**——这是给"不会前端"的你最关键的区分：

- **生成质量**：AI 能不能一次写对
- **排错成本**：写错之后**你能不能自己看懂并修**（权重远高于生成质量）

| 维度 | A：Tauri+React | B：PySide6 | C：NiceGUI/Streamlit | D：Electron |
|---|---|---|---|---|
| ① 学习成本（你：不会前后端） | **2** — 要同时碰 Node/npm、React Hooks、TS、Vite 配置、Rust 工具链 | **4** — 只需 Qt 的"控件+布局+信号槽"三个概念 | **5** — 只写 Python 函数 | **2** — Node 生态 + 进程间通信 |
| ② AI 生成质量 | **5** — 训练数据最多 | **4** — 成熟 API，样本多 | **4** | **5** |
| ② AI **排错成本**（反向，5=好修） | **2** — 报错来自 npm/tsc/Cargo，看不懂 | **5** — 报错就是 Python traceback | **4** — 但窗口控制属冷门，AI 常答错 | **2** |
| ③ MVP 开发效率 | **3** — 已跑通，但小改动也要过前端构建链 | **5** — 改一行 Python 重开即可 | **2** — 前 80% 极快，最后"贴边+不抢焦点"卡死返工 | **2** |
| ④ 社区与文档 | **5** — Tauri 112k★ / React 生态巨大（issues 1485，活跃但问题多） | **5** — Qt 官方文档质量顶级、中文资料多、二十年积累 | **3** — NiceGUI 16.3k★/57 issues，小而活跃，但桌面窗口场景资料稀缺 | **5** — 123k★/744 issues |
| ⑤ 硬需求契合（无焦点/贴边/跟随） | **4** — 靠 Python 侧补实现，跨进程按标题找窗口 | **5** — Qt 原生 + 现有 docker.py 完全复用 | **1** — 不具备 | **3** — 可行但要折腾 `setFocusable(false)` |
| ⑥ 长期可维护性（你自己改） | **2** | **5** | **3** | **2** |
| **合计** | **23** | **33** | **20** | **19** |

## 四、数据库单独说

| 选项 | 结论 | 理由 |
|---|---|---|
| **SQLite** ✅ 推荐 | 标准库 `sqlite3` 自带，**不用装服务、不用起进程**，一个 `.db` 文件 | 消息去重要存 msgid、话术库要存分类、配置要持久化，SQLite 全够；需要检索时上 `FTS5` |
| JSON 文件 | 可用，仅建议第 1 天 | `config.json` + `history.jsonl`；超过几千条后查询/去重开始难写 |
| MySQL / PostgreSQL | ❌ 不推荐 | 桌面单机场景要额外装服务、配账号、处理开机自启，零收益 |
| Redis / MongoDB | ❌ 不推荐 | 同上，且引入新的运维面 |

**建议**：MVP 直接 `sqlite3` + 一张 `messages(id, chat, sender, type, content, ts)`、一张 `quick_replies(tag, content)`。
等表超过 3 张、想让 AI 少写 SQL 时再引入 **SQLModel**（FastAPI 同作者，AI 生成极其稳定）。

## 五、部署方式单独说

| 方式 | 结论 |
|---|---|
| **PyInstaller** ✅ 推荐 | 一条命令出 exe；`--noconsole --onefile`，用 `--add-data` 带上 `.env` 和静态资源。注意把 `wxauto`、`comtypes`、`pywin32` 加进 `hiddenimports` |
| Nuitka | 需要时再说（启动更快、反编译更难），但编译耗时长、踩坑多，MVP 不用 |
| `tauri build`（msi/nsis） | 只在方案 A 下需要；但 Python 后端仍要单独打包 → **两个产物、两套发布流程** |
| Docker / 云部署 | ❌ 不适用：容器里没有可交互桌面会话，wxauto 依赖真实前台窗口，UIA 也拿不到真实窗口 |
| 开机自启 | 放 `shell:startup` 快捷方式，或写注册表 Run 项 |

## 六、AI 编程工具支持度：怎么用才不出事

1. **让 AI 先出"最小可运行骨架"，不要一次要完整功能**。骨架跑起来再加功能，否则一次几百行出错时无从下手。
2. **每个技术栈的 AI 高频出错点**（提前告诉 AI 能省一半时间）：
   - PySide6：跨线程更新 UI（必须用信号槽，AI 常在子线程直接改控件）；`QThread` 里别创建控件
   - Tauri：Rust 编译错误看不懂、前端 `fetch` 跨域/端口不对
   - React：`useEffect` 依赖数组导致重复请求、闭包拿到旧 state
   - wxauto/UIA：窗口在前台、缩放 100%、控件树变化
3. **给 AI 的上下文要带"硬约束"**：每次让它改 UI 时，都附带一句"这个窗口必须 `WS_EX_NOACTIVATE`，不能抢微信焦点"，否则它会好心帮你加自动聚焦。
4. **验证必须由真人做**：AI 无法验证"窗口有没有贴到微信右边""焦点有没有被抢"。这类验收只能你手动点。

## 七、推荐结论

### 推荐：方案 B —— PySide6（UI）+ FastAPI（后端）+ SQLite（数据）+ PyInstaller（打包）

**五条理由**

1. **你的错误信息永远是 Python traceback。** 这是"不会前端"的人最大的护城河 —— 方案 A/D 里一旦 npm、tsc、Cargo 报错，你只能把整段报错丢回给 AI 猜。
2. **全栈一种语言**：同一个进程里既能调 `pywin32` 做窗口控制，又能调 wxauto 收消息，不用设计跨进程通信。
3. **Qt 原生满足硬需求**：`FramelessWindowHint | Tool | WindowStaysOnTopHint | WindowDoesNotAcceptFocus` 四个 flag 就解决了"无边框 + 不抢焦点 + 置顶"，再叠上现有的 `docker.py` 做位置跟随。
4. **社区与文档质量顶级**：Qt 二十多年积累，官方文档规范，中文书籍/教程极多；不像 wxauto 那样存在停维护风险。
5. **不是推倒重来**：现有代码里，`adapters/`（采集层）、`services/`（AI + 贴边）、`server.py` 全部 **零改动复用**，只是把 `web/` 那一层换成 `desktop/`（PySide6 UI，约 300 行）。这正是当初把采集层抽象成 Adapter 的收益兑现。

### 什么时候该坚持方案 A（Tauri+React）

- 你非常在意界面颜值/动效，且**愿意为此额外学 Node+Rust**
- 未来打算把这个壳复用到别的平台（macOS/Linux）
- 或者你打算把 UI 部分长期交给 AI 维护，自己完全不碰前端代码

> 现实折中：**原型 A 已经跑通了**，如果你只是想先用起来、不打算自己大改，就继续用 A；如果你要长期自己维护迭代，现在切 B 的成本最低（再往后拖，UI 逻辑越多越难切）。

## 八、"不推荐，但很多人用"的选项

| 选项 | 为什么很多人用 | 为什么不推荐 |
|---|---|---|
| **Electron + Python sidecar** | 前端人做桌面外挂的默认选择；生态最大 | 体积 150MB+；要维护 Node 依赖和打包链；Python 要当 sidecar 一起打包（两个运行时）；无焦点窗口要额外处理；启动慢。对你（不会前端）是三重负担 |
| **Streamlit / Gradio** | 做 AI demo 最快，几行出界面 | **根本不合格**：它们是 Web 应用，跑在浏览器标签页里，无法贴边、无法不抢焦点、无法跟随微信窗口。微信一操作就被浏览器盖住 |
| **NiceGUI** | 纯 Python 写界面，看起来最省事 | 同上：默认跑浏览器；`native` 模式虽基于 pywebview，但**没有稳定的置顶/无焦点/跟随 API**，属冷门路径，AI 常给错答案 → 高返工风险 |
| **Django** | 学 Python 后端的人第一反应 | 桌面单机场景用不上 Admin/中间件/会话那一整套；同步为主，对 win32 自动化无收益；白白增加心智负担。要 HTTP 就 FastAPI/Flask 足够 |
| **MySQL / Redis / MongoDB** | "正经项目都该有数据库"的惯性 | 需要装服务、开机自启、配账号；单机桌面零收益 |
| **Docker 部署** | 部署习惯性方案 | 容器里没有可交互的桌面会话，wxauto 依赖真实前台窗口，UIA 也拿不到真实窗口 —— 物理上不可用 |
| **Flask + 原生 HTML/JS（jQuery）** | 老教程多、"简单" | 你会陷入手写 HTML/CSS/JS —— 正是你说不会的部分；且同样跑在浏览器里，遇到约束 2 照样返工 |

## 九、验收口径与下一步

MVP 完成的**可验收标准**（必须真人手动验，AI 验不了）：

1. 微信收到新消息 → 侧边栏 3 秒内显示（开启监听时）
2. 点"生成回复" → 5 秒内给出建议文本
3. 点"发送" → 消息确实出现在微信会话里
4. **点侧边栏任意位置后，直接打字，字进的是微信输入框**（= 没抢焦点）—— 这条是本项目成败线
5. 拖动/最大化/最小化微信 → 侧边栏跟随，不脱离、不遮挡

**剩余风险**：wxauto 停维护且绑死微信 3.9.11.17（已用 Adapter 隔离，换 4.x 只需新增一个 Adapter）；个人微信自动化违反用户协议，有封号风险，仅限自用。

**下一步**（你点头我就执行，会先出实施计划）：
把 `web/`（React）替换为 `desktop/`（PySide6），后端与贴边逻辑不动；预计新增约 300 行 Python、删除全部 Node/Rust 构建链，MVP 迭代从"改代码→跑构建→刷新"变成"改代码→重开窗口"。
